What's new in XenForo 1.5.51

Release candidate. Local upgrade tests and the concluding comparison panel are complete; separate full-source checkpoints await transmission approval. Read the preparation instructions before replacing existing code.

Changelog

  • Fixed validated-IP DNS pinning for hosts with multiple IPv4/IPv6 addresses. A single comma-separated cURL rule retains fallback addresses. Default untrusted fetches fail closed on unsupported libcurl. Ordinary administrator and caller transport options are preserved while pinning, TLS and redirect policy remain enforced.
  • Fixed tag URL collision queries on MySQL 8.0.22 and newer by removing binary regular-expression arguments.
  • Fixed false rejection of object-like text inside serialized strings. Native decoding prevents application object construction, validates decoded values and rejects excessive nesting.
  • Validated deferred data before the atomic claim. Throwable and fatal recovery retain decoded data; automatic failures retry after five minutes.
  • Restored the stock signing default for fresh upgrades and added a mandatory salt preparation tool for existing installations.
  • Preserved Facebook/Google option rows for XF2 migration while masking retired XF1 integration reads and rejecting their registration endpoints.
  • Added the lowercase cookie.samesite alias with the legacy sameSite fallback, and aligned the native installer checks and message with the documented PHP 7.3/7.4 range.
  • Added a read-only migration preflight, including pending job and mail-queue counts, and corrected the missing-tool cleanup instructions.
  • Removed the five Zend files' deprecated curly-brace offset syntax identified by the previous PHP 7.4 lint pass.
  • Added a reproducible release builder, native file-health sums and a SHA-256 package manifest. Template and phrase XML payloads remain unchanged. No schema changes are introduced; user/content IDs, authentication formats and attachment layout are retained. Native upgrades may rebuild internal phrase IDs and cache metadata.

Before upgrading

Back up the matched database and files. Before uploading new code, run php tools/prepare-upgrade.php /path/to/forum --apply using the old installation. This writes its current effective salt into library/config.php without printing it. Run preparation as the site owner with the same configuration and environment as the forum. Configuration is loaded once, including ordinary helper-function definitions. File ownership and permissions are preserved. The upgrade refuses to finish without an explicit salt. Keep the tools outside the public forum directory.

Detailed changes and design

HTTP policy and supported transport

The previous resolve list repeated the same host and port, discarding earlier addresses. 1.5.51 sends one rule containing all validated addresses, IPv4 first. Hostname verification and TLS peer verification stay enabled; redirects are revalidated. The default path requires cURL 7.59 or newer and never falls back to a second unpinned lookup. An explicitly configured custom transport remains the administrator's responsibility.

Safe serialization and recoverable jobs

The old regular expression mistook strings such as ;O:8:"stdClass":0:{} for embedded PHP objects. The PHP decoder now uses allowed_classes=false and validates the resulting values. Objects, cycles, nesting deeper than 128 and traversals exceeding 100,000 values are rejected. Serialized false remains supported. Invalid manual jobs stay in their original rows and raise a visible error before deletion. Invalid automatic jobs are held for operator review, logged once, and excluded from normal polling. Preflight reports their held counts; repair and reschedule them explicitly. Job execution still requires an atomic delete claim. The claim also compares the validated snapshot, so a producer update arriving before the claim is retained for a fresh worker. Writes after the claim still follow XF1 coalescing rules and can be superseded by a continuation or retry. Stop producers before draining work for cutover. Competing workers do not execute a successfully claimed row twice.

Recovery stores the already decoded data. Throwable failures retain both manual and automatic jobs. Automatic jobs retry after five minutes. A process or connection failure during requeue can still prevent recovery; operators must inspect logs. Retries can repeat partial side effects, so job implementations still need idempotency. This is an XF1 repair, not an XF2 scheduler backport.

Signing-material continuity

1.5.50 changed the implicit salt. Restoring the original default blindly would rotate existing 1.5.50 sites again. Preparation therefore pins whichever salt the old installation actually uses, including a custom explicit salt. It checks that old code and database versions agree before inferring an implicit value. New file defaults use the stock XF1/XF2 constant. Pinning does not guarantee that old XF1 cookie or email-action URL formats remain accepted by XF2.

Provider data and retired integrations

Updated 1.5.50 upgrade step 1 retains the original provider option rows. Runtime accessors return empty values for the retired providers, and registration endpoints return 404. The native XF2 upgrader can read the stored settings directly. An installation that already used the original destructive 1.5.50 step needs private backup recovery or reconfiguration. Association rows are preserved separately. XF2 can activate retained provider configuration during conversion. Decide whether to expose it before reopening the site. Live OAuth validity and callback configuration still need operator testing.

Cookies and configuration mapping

An explicitly configured lowercase cookie.samesite takes precedence; otherwise XF1 keeps its existing camel-case alias and Lax default. XF2 reads the lowercase spelling. Its Secure flag follows HTTPS request detection, so the target proxy must supply trusted scheme information and strip spoofed inbound forwarding headers. Preflight lists dropped custom keys and maps known settings without printing their values.

Storage, extensions and native conversion

Preflight inventories auth schemes, provider presence, pending jobs, queued-mail count and oldest date, malformed array options, add-ons, custom templates, paths and transport requirements. It streams queued payloads rather than retaining all of them in memory. Preflight performs no SQL updates or file writes. A separate cleanup tool reports by default and removes only the four documented obsolete paths with explicit --apply; it refuses an XF2 tree and linked ancestors, and never follows directory symlinks. Run it before uploading XF2. The supplied target ZIP contains some of the same legacy asset paths, so do not reuse XF1 cleanup rules after conversion. Keep serialized array options and authentication data in their native formats until XenForo's upgrader converts each field. Do not copy the XF2 ORM, container or vendor tree into XF1.

XF2 drops the old deferred table, clears queued XF1 mail, disables legacy add-ons and removes old style-specific templates. Drain or reconcile both business jobs and queued mail and plan supported extension successors before moving the site. Use a separate Unicode conversion window after the core upgrade. The supplied historic 1.5.50 changelog remains in this package for reference; these release notes supersede its credential-clearing and missing-build-script instructions.

Tested upgrade stages

The complete 1.5.24 → original 1.5.50 → corrected 1.5.51 → native 2.3.13 lab sequence passed. Final 1.5.51 checks include 1,244 native file hashes, 2,296 PHP files, 16 queue assertions, 15 serialization assertions and six HTTP option-policy assertions. Both authentication schemes, preserved mail-job delivery to local files, provider migration, attachment bytes and an independent matched restore passed. XF2 completed 57 native upgrade versions on PHP 8.3.36; real loopback HTTPS checks passed. Checkpoint 1 consult-panel is complete. Checkpoints 2 and 3 await approval for external transmission; this remains a release candidate until those reviews and final report signoff finish.

Direct versus staged migration

Two stock 1.5.24 direct upgrades and the complete staged path reached 2.3.13 through 57 native XF2 upgrade versions. The prepared direct path and staged path have identical tested schemas across 225 tables, semantically equal rows under the documented date/phrase/history rules, matching permissions, and byte-identical compared target files. The staged path required private recovery of settings erased by original 1.5.50. Direct migration needs no wmtech data-format bridge.

The unprepared direct route lost its pending XF1 business row, retained a different fixture URL and emitted no explicit SameSite attribute. Either route needs preparation, a stopped-writer queue drain and reviewed target configuration. Endpoint snapshots precede HTTP sign-in and native post-upgrade job completion; eventual job convergence is untested. Both accounts and attachment downloads passed later trusted-loopback HTTPS checks on each endpoint.

The concluding consult-panel used Claude Opus 5.5 and Z.AI GLM 5.3 Flash on sanitized results and author-written comparison methods. All 33 quoted anchors verified. This comparison review does not replace the pending full-source implementation reviews. The current email-verification test also narrows the original salt finding: stored account-verification records survive the tested salt change, while the derived EmailStop/unsubscribe key changes.

Runtime security and limits

Target application compatibility is PHP 7.3/7.4. This package does not patch the PHP engine or certify every add-on, style or integration. Verify current vendor engine fixes before deployment. No PHP 8 compatibility is claimed for XF1. Password-reset redesign, blanket password truncation and structural XF2 backports remain deferred.
