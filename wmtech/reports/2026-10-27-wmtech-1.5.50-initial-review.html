Findings requiring correction

P1F-01 · verified

Outbound requests lose IPv4 fallback

upload/library/XenForo/Helper/Http.php:112–127

What this is
Image proxying and automatic link-title retrieval now pin requests to validated DNS addresses. The goal is to prevent a second DNS lookup from redirecting a request to a private address.
Problem
The loop emits several cURL resolve entries with the same hostname and port. Each replaces the preceding address list. Because IPv6 addresses are appended last, a dual-stack host is left pinned to one IPv6 address. On the IPv4-only test network, the patched helper failed for all three public hosts while stock succeeded.
Smallest correction
Emit one HOST:PORT:ADDRESS[,ADDRESS] entry containing all validated addresses. Keep TLS verification and per-redirect URL checks. Multiple addresses per entry require libcurl 7.59 or later; older supported deployments need retries restricted to validated addresses.
Consequence if unchanged
Normal external images and link titles can fail. Multiple IPv4 records also lose failover.
Verification
A one-entry pin containing the same validated addresses returned HTTP 200 for example.com and www.php.net, using PHP 7.4.33 / libcurl 7.74.0 with certificate verification enabled. Evidence.

P1 · MySQL 8F-02 · verified

The tag query change breaks modern MySQL

upload/library/XenForo/DataWriter/Tag.php:139; upload/library/XenForo/Model/Tag.php:460

What this is
Two tag-slug queries change from REGEXP ? to REGEXP BINARY ?.
Problem
MySQL 8.0.22 and later reject binary regular-expression arguments. The actual XenForo tag_url column is VARCHAR(100) with utf8_general_ci collation. Both original methods returned cafe-3 for an existing cafe-2 row; both patched methods failed on MySQL 8.4.10. Direct SQL reported error 3995.
Smallest correction
Remove BINARY from both queries. If a deployment needs case-sensitive matching, test an explicit compatible text collation against its schema.
Consequence if unchanged
New tag creation can fail during thread posting and other tag-writing operations. MariaDB 10.6 passed the corresponding tag test.
Verification
Original and patched methods were run on the same PHP 7.4.33 runtime, the same MySQL 8.4.10 server, and the table definition shipped by XenForo. Evidence.

P2F-03 · verified

Valid queued text can crash and lose a background job

upload/library/XenForo/Model/Deferred.php:259, 272–296; upload/library/XenForo/Helper/Php.php:200–210

What this is
Deferred execute_data is newly passed through the existing safeUnserialize helper. Bulk email and mass-conversation text are carried in those arrays.
Problem
The helper scans raw serialized bytes for object-looking syntax before decoding. Ordinary email text containing a PHP serialization example is a false positive and turns the entire array into false. The queue row is deleted before execution. Passing false to the array-typed runner raises TypeError; recovery applies the same decoder and raises another TypeError.
Smallest correction
Use native deserialization with allowed_classes=false on these PHP 7.x paths, respecting string boundaries. Validate the decoded array before dispatch and preserve original job data during error recovery.
Consequence if unchanged
A valid text-bearing job can fail permanently and lose its queue entry.
Verification
The identical payload completed under stock code with mail delivery disabled. Patched execution and recovery failed, and the queue row was missing afterward. The Exception-only recovery weakness predates 1.5.50; the new decoder call introduces this valid-text trigger. Evidence.

P2F-04 · verified

An undocumented salt change invalidates existing signatures

upload/library/XenForo/Application.php:701; upload/library/XenForo/Model/User.php:1456,1461

What this is
globalSalt contributes to remember-me cookies, email-stop/unsubscribe signatures, proxy HMACs and mail-bounce authentication.
Problem
The upgrade changes the default globalSalt. Boards without an explicit config override therefore switch signing material. Pre-upgrade remember-me cookies failed over HTTP while newly issued cookies logged in. Email-stop and proxy signatures also stopped matching the same stored inputs.
Smallest correction
Preserve the prior default in the compatibility patch. For an individual deployment, pin its current effective salt in library/config.php before upgrading. Treat intentional rotation as a separate migration.
Consequence if unchanged
Automatic login fails after current sessions expire, existing email-stop/unsubscribe links can fail, and previously signed proxy URLs become invalid. Current sessions and password hashes are not automatically invalidated by this change.
Verification
Pre/post signatures were compared using the same user and proxy key. The HTTP cookie comparison independently confirmed the remember-me regression. Evidence.

Limits and operational notes

  • The upgrade deliberately clears Facebook and Google credentials. Treat that as an explicit product decision when planning deployment.
  • Legacy Azure, Flash and Facebook files remain after an overlay unless removed separately. The shipped manifest ignores those leftovers. Cleanup/build scripts mentioned in the package instructions are absent from the ZIP.
  • The application suppresses E_DEPRECATED globally. A quiet error log alone does not establish compatibility across unused libraries or add-ons.
  • An isolated report-handler crash was investigated and rejected as a new report vulnerability: the existing report writer blocks that crafted content before insertion. F-03 survives this boundary check because the deferred queue accepts the text on its write path.
  • No production add-ons/styles, production database, browser-executed JavaScript, live PayPal callbacks, social authentication, email delivery, proxy deployment or load/concurrency behavior were tested.

PHP 7.4 reached upstream end of life on 28 November 2022. This XenForo patch does not itself maintain the PHP interpreter. The status of separately supported vendor runtimes was outside scope.

28 October follow-up and corrected scope

The four findings were reproduced again against the archive-derived 1.5.24 and original 1.5.50 code. The 1.5.51 candidate corrects them and passed the full staged upgrade, a direct 1.5.24 upgrade, focused queue/serialization/HTTP tests, file health and an independent matched restore. Stock control, original patch and corrected control retain the differential outcomes.

F-04's earlier account-confirmation wording was too broad. The historic test field called confirmation measures getUserEmailConfirmKey, consumed by EmailStop/unsubscribe flows. A native stored-record control on 1.5.51 keeps an account email-verification record valid after a salt change and rejects a wrong key. No password-reset or cross-major URL continuity claim follows from this test.

The direct-versus-staged report records equivalent tested XF2 endpoints after preparation and the meaningful configuration, queue and leftover-file differences. Stage 1 and the concluding comparison panel are complete. Full-source checkpoints for the candidate and final staged conversion remain pending explicit external-transmission approval. The package remains a release candidate.

Retained implementation evidence: candidate validation manifest, stage 1 panel verification and final artifact checks. Local stages 2 and 3 passed; their separate full-source external reviews remain open.
