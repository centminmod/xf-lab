2. What changed across the three codebases

XenForo 1.5.24

Underscore-named classes, Zend components, models and DataWriters. PHP-serialized options, authentication data and deferred jobs form part of the persistence contract.

The original lab established the PHP 7.2 baseline.

wmtech 1.5.50

Retains the XF1 architecture and data model. Adds PHP 7.4 compatibility and selected HTTP, cookie and session controls. Its installer also retires integrations and adjusts legacy options.

It changes 45 existing files and adds three. A working upgrade remains possible without a framework rewrite.

XenForo 2.3.13

Uses namespaces, an application container, entities, repositories and services. Field declarations distinguish serialized and JSON data. Jobs use conditional claims and explicit results; HTTP code separates trusted and untrusted requests.

Its native upgrade sequence converts XF1 data selectively.

The useful design lesson is to make boundaries explicit: validate untrusted requests, retain recoverable job data, declare each storage format, and give upgrades ordered, testable steps. Copying the XF2 container, ORM or vendor tree into XF1 would enlarge the compatibility burden without helping the native conversion.

XF2 still serializes authentication and job data. It is not an instruction to convert every XF1 field to JSON. Its 2.0 upgrade step 25 expects PHP-serialized array options; premature JSON becomes an empty array in the tested native decode expression. Other steps convert profile fields and connected-account settings themselves.

3. Verified findings and migration consequences

Priorities below describe the affected deployment. P1 warrants correction before using that configuration; P2 needs correction or an explicit migration action. Expected native conversion behavior is identified separately from patch defects.

M-01 · P1 when usedProvider credential clearing removes native migration input

wmtech's 1055070 step 1 blanks facebookAppId, facebookAppSecret, googleClientId and googleClientSecret. XF2's 2.0 step 43 later reads those exact option rows into xf_connected_account_provider. The rehearsal ended with both providers unconfigured.

Retiring the broken XF1 login flows does not require destroying the settings needed by a successor. Preserve the original option values and disable the retired UI and endpoints explicitly. A private operator backup is a recovery measure; an automatic plaintext secret export is not the preferred patch design. The report must never print credential values.

Sites already on 1.5.50 need a private pre-patch backup or provider reconfiguration. Linked-account associations use a separate table that XF2 renames; this review did not test live provider login or prove that old credentials remain valid today. Verify the provider application and callback configuration before enabling it.

Introduced by library/XenForo/Install/Upgrade/1055070-1550.php:25–32; migration consumer src/XF/Install/Upgrade/2000010-200a.php:2010–2056. Observed provider state.

M-02 · P2Copied configuration can lose its meaning

The native translator copies only explicitly configured, allowlisted values. It copies the whole cookie array, but wmtech uses cookie.sameSite while XF2 reads cookie.samesite. A copied Strict setting produced no SameSite attribute in the fixture.

XF2 also overwrites the cookie secure default with request HTTPS detection. With secure=true and a request detected as HTTP, the emitted cookie had no Secure flag. That reproduces a configuration mismatch; it is not a demonstrated remote exploit. Behind TLS termination, configure the origin to recognize HTTPS and have the edge replace untrusted forwarding headers with trusted values.

Add an explicit mapping report. A backward-compatible lowercase samesite alias in the next XF1 patch is a small candidate change; retain the existing camel-case fallback until callers migrate. Validate Strict, Lax and any required None policy on the actual target runtime. An XF1 config default that was never written to config.php will not migrate automatically.

The allowlist drops wmtech's session overrides, HTTP user agent, branding, jQuery, PayPal TLS and untrusted-client settings. Some have different XF2 configuration or application controls. Map each intended behavior rather than copying unknown keys. For example, review target http.proxy and http.sslVerify; do not carry a legacy TLS-disable override into a new deployment without a reason.

Translator src/XF/Install/Upgrader.php:453–505; cookie construction src/XF/App.php:462–474; src/XF/Http/Response.php:342–366; HTTPS detection src/XF/Http/Request.php:2044–2053. Translation test · Cookie test.

M-03 · P2 operationalPending XF1 work does not enter the XF2 queue

Native 2.0 step 1 drops xf_deferred. The fixture had one pending manual business job before conversion and none afterward; the old table no longer existed. This is expected upstream behavior. New XF2 rebuild jobs do not represent delivery of old business work.

Repair the verified XF1 decoder defect before attempting a drain. Inventory pending jobs by class, manual flag and age, stop new producers, complete or explicitly reconcile the work, and check the queue again immediately before cutover. Add-on-specific work needs its own disposition. A blanket deletion is not a successful drain.

Native step 21 also disables legacy add-ons. Step 22 deletes style-specific and add-on templates, with exceptions for particular custom templates. Replacement XF2 add-ons and rebuilt styles require planning even when core conversion succeeds. These are not defects introduced by wmtech.

XF2's HTTP reader retries validated IPs with CURLOPT_CONNECT_TO; its job manager uses a conditional trigger-date claim and catches Throwable around job execution. These mechanisms explain the intended behavior. They are not drop-in XF1 replacements. Job-runner construction happens before that catch, so XF2 is not proof that every decode failure is recoverable.

Keep the queue claim before execution. Moving pure validation before the claim does not allow two workers to execute the job, because both still need the successful atomic deletion. Moving the deletion after execution would create a duplicate-work risk.

Stock XF1 and XF2 share the recorded default salt, while wmtech uses a different one. An explicit salt survives native config translation. This does not promise that XF1 cookies or confirmation URLs remain valid in XF2; the cross-version token formats were not tested. Password continuity was tested separately.

4. Proposed next wmtech maintenance release

The release should preserve database schemas, content IDs, authentication scheme names, serialized formats and attachment paths. Keep a new XF1 version ID above 1055070 and below 2000010. Existing sites do not rerun completed upgrade steps; fresh upgrades must also avoid the original destructive provider step.

Let XF2 handle entities, services, repositories, its own job scheduler, connected-account conversion and authentication class renames. The XF2 add-on structure provides legacy_addon_id for supported successors; it does not translate XF1 executable code. Preserve file layout and content hashes until the native upgrader finishes, and use independent SHA-256 checks to verify transferred files.

Defer the user-chosen password-reset backport unless XF1 must remain in service long enough to justify testing the full token, email, template and session lifecycle. Defer blanket password truncation and private-TLD parity changes until their actual exposure and legacy compatibility are established. The panel supplied no reproduced new vulnerability for either hypothesis.

6. Procedure for a site currently on 1.5.50

Runtime gate, checked 27 October 2026. PHP's 21 October advisory identifies critical engine vulnerabilities CVE-2026-109618 and CVE-2026-109619. Its fixed supported releases include 8.3.36. The cached lab image reports 8.3.33; no vendor backport provenance was verified. PHP 7.4 needs documented vendor fixes or the exceptional source backports. wmtech's application patch does not apply engine fixes. Rehearse on a verified patched target before production. PHP security advisory.

The supplied 2.3.13 requirements declare PHP 7.2 and MySQL 5.7 minimums. The official release announcement recommends PHP 8.3 and includes application security fixes. Minimum compatibility does not establish engine security or extend XF1 support.

  1. Inventory the live deployment. Record exact code/archive hashes, effective salt, configuration overrides, database/charset, authentication schemes, linked providers, add-ons, custom styles, queues and data paths. Export presence and counts into the report; store any recovery secrets privately.
  2. Correct the known patch regressions in a separately reviewed release. Preserve original provider settings for fresh upgrades and recover or reconfigure settings already cleared. Run focused tests before draining jobs.
  3. Clone representative site data into an isolated environment with outgoing mail and payments disabled. Map each required add-on to a supported XF2 successor, including its data migration instructions. Rebuild styles and test custom permissions and authentication.
  4. Prepare a verified patched PHP target and supported database. Translate configuration explicitly, check HTTPS/proxy behavior and emitted cookies, and preserve native storage formats. Do not pre-convert array options or spoof the version ID.
  5. Enter a maintenance window, stop external writers and cron/job producers, and drain or reconcile pending business jobs. Take a matched database and file backup after writes are frozen. Prove a restore into another isolated instance before treating rollback as available.
  6. Merge the XF2 distribution into the existing installation while preserving data and internal data. Have the native web upgrader generate the legacy configuration translation, or prepare and review the equivalent src/config.php before CLI use. The CLI refuses to operate with only the legacy config file. Run the native upgrade and required rebuilds.
  7. Compare content IDs/counts and attachment hashes; verify permissions, URLs, search, every authentication scheme, password reset, providers, uploads, mail queues and payment callbacks as applicable. Test the real TLS edge. Reconcile any skipped or unsupported add-on data before reopening writes.
  8. Handle rollback by restoring the matched pre-upgrade database and files together. Define a cutover decision point before reopening writes, because new production writes make rollback a data-reconciliation problem.
  9. After the core upgrade is stable, schedule Unicode conversion separately if wanted. Use php cmd.php xf:convert-utf8mb4 before enabling fullUnicode, with its own backup and verification. Follow the official Unicode procedure.

The official upgrade guide permits direct upgrades from prior releases. The successful fixture confirms that wmtech's 1055070 fits the supplied 2.3.13 upgrade ordering; an intermediate XF2 release was not needed in this test.

7. External verification and chair decisions

The requested external review used consult-panel's lean roster, Claude Opus 5.5 and Z.AI GLM 5.3 Flash, both at high effort. Both returned usable complete responses. No provider was dropped, no tie-breaker was added, and no cross-review ran. Codex remained the local verifier.

The deterministic checker found 69 quotations at their supplied ranges and relocated one range by one ending line. All 70 quotations were usable. One malformed finding label in a citation manifest was normalized without changing its quote. Repeated-quote warnings were checked against the intended source ranges. Every citation claim was accounted for in the final run record. The final fingerprint matched the pre-panel tree before this report was created.

Both reviewers supported retaining XF1 contracts and the original four findings, provider/configuration hazards, native job loss, and the narrow maintenance scope. Their agreement did not replace the source and runtime checks.

  • Claude preferred retaining provider options in the database while disabling their runtime use. Z.AI preferred export-then-clear. The chair chose retention because XF2 reads the original rows, and automatic secret exports introduce extra handling and manual migration.
  • Claude proposed decoding before the existing queue claim. Z.AI described XF2's lease model. The chair chose validation before the current atomic claim and better recovery; a scheduler rewrite is unnecessary for this bridge.
  • The chair rejected Claude's suggested unpinned fallback for old cURL as the preferred fix. Pinning must remain part of the supported security contract.
  • The chair rejected unsupported fixture descriptions that Twitter migrated configured and that no pending job had existed. The retained fixture has no Twitter assertion and explicitly seeded one job.
  • Long-password exposure, private-TLD parity, early-upgrader custom-auth fallback behavior and cross-version signature continuity remain unverified. They were not promoted into confirmed vulnerabilities.

8. Limits and retained evidence

This was a scoped adversarial comparison, not a complete audit of every file in XF2 or a production sign-off. The fixture is deliberately small. Real add-on code, custom styles, live OAuth, PayPal/IPN, SMTP delivery, production TLS forwarding, full browser JavaScript behavior, concurrency under load, large-board upgrade time and a complete rollback rehearsal were not tested. The inert add-on row verifies core disabling behavior only.

The 2.3.13 release includes security fixes, but this review does not claim that every upstream security change applies to XF1 or that wmtech incorporates it. The tested target runtime needs a separate security-provenance check. Proposed maintenance changes and their production acceptance tests remain to be implemented.
