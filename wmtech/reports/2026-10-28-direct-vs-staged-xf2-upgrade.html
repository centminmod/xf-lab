Direct and staged upgrades to XenForo 2.3.13

Use the native direct route when the site is ready for XF2. The prepared direct route and the staged route reached the same tested schema, content, authentication storage and permissions. Passing through wmtech does not add a required migration format. 1.5.51 is useful when XF1 must remain in service before cutover.

This report adds the requested endpoint comparison to the initial patch review and evolution review. It covers observed results and comparison methods. The separate full-source external reviews of the 1.5.51 implementation remain pending explicit transmission approval.

Method and controlled inputs

Both direct runs restored the same saved database and files used by the staged replay. The provenance records bind the two direct runs to those inputs; the staged replay uses that baseline by its recorded protocol. The small fixture contains two users, one thread/post, one attachment, two linked providers, an inert add-on and a pending business job. Shared fixture completion supplies its sender/format fields without changing its object-like body text and rebuilds the provider association cache. These corrections were also made in the staged run.

All target runs use the same supplied 2.3.13 ZIP, PHP 8.3.36 image and MariaDB 10.6 service. Native upgrade selection completed 57 XF2 versions per path, starting at 2.0.0 Alpha. The direct runs do not install wmtech core code. Private data snapshots were captured on idle clones after the native upgrade/rebuild commands and before interactive HTTP logins. Fifteen native XF2 jobs remain queued on each endpoint, including search, embed metadata, icon usage, like accounting, cleanup, cron and upgrade checking. Their class/data/manual fields match, but eventual post-job convergence was not tested. Later logins can create sessions, activity records and password rehashes.

Why the raw database snapshots differ

The nine raw differences are xf_cron_entry, xf_data_registry, xf_job, xf_option, xf_phrase, xf_phrase_map, xf_style, xf_template and xf_upgrade_log.

The comparison retains all other values. It replaces only the declared generated dates/version markers and accounts for the two extra history entries. It compares phrases by language/title while preserving every other phrase field; every phrase-map reference resolves to the corresponding logical phrase. All 11,213 phrases and 22,426 map rows are covered. Internal phrase IDs can be reallocated by native rebuilds, so the earlier promise to preserve IDs is narrowed to user/content IDs.

The decoded registry entries are bound to the exact serialized input bytes. Negative controls detect altered user email, auth bytes, provider configuration, phrase text and cron rules; stale decoded cache input is refused. No salt, credential, content value, permission value, cron rule or job payload is normalized away.

The unchanged-config direct run also retains fixture boardUrl port 8772, while the XF1 upgrade harness set 8774. The prepared direct control aligns that fixture URL. Its only remaining loaded configuration difference is globalSalt. The plain run's two remaining normalized-table differences are the URL option and its registry mirror; they are fixture metadata. A separate field-level check computes exactly options.boardUrl in the normalized registry and boardUrl in options. Registry key-order differences are zero on both direct controls.

Corrections prompted by this comparison

Cleanup boundary. The supplied 2.3.13 ZIP reintroduces four Flash asset files not covered by its native hash manifest. Their presence is not a demonstrated vulnerability. The XF1 cleanup now refuses a tree containing src/XF.php, because the old XF1 Application.php can remain after an XF2 overlay. Tests prove refusal before deletion and normal allowlisted XF1 cleanup. Run it before uploading XF2. The supplied native xf:file-clean-up XF command is limited to selected src directories and does not remove the old XF1 library tree. Review legacy/custom dependencies separately.

Salt-impact wording. The historic evidence field called confirmation uses getUserEmailConfirmKey for EmailStop/unsubscribe links. It is not an account-verification nonce. A native 1.5.51 stored email-verification record remains valid after a salt-only change; a wrong key is rejected and the transaction is rolled back. The derived email-stop key changes. The original finding remains valid for remember-me continuity and the other verified signing consumers; account-email-verification breakage was overstated.

Decision and limits

1.5.51 release candidate ZIP · Changelog and detailed release notes · Final artifact checks · Compact comparison-panel record

Choose the native direct route when add-ons, styles, operations and the target runtime are ready. Apply the same migration preparation: matched backup/restore, credential inventory, job and mail-queue drain and explicit target configuration. Finish and inspect native XF2 post-upgrade jobs before reopening writes. Use 1.5.51 when an XF1 maintenance interval is needed, or to repair an existing 1.5.50 installation before cutover. Do not install original 1.5.50 solely as a stepping stone to XF2.

This is a small synthetic test. It does not establish production add-on/style compatibility, live provider/payment/SMTP validity, complete browser JavaScript behavior, production proxy correctness, large-board timing or concurrency. The matched 1.5.51 restore and loopback TLS were tested. PHP 7.4 engine backport provenance remains unverified; the target run uses PHP 8.3.36. Unicode conversion remains a separate operational step.
